# Домашняя работа 2 — MongoDB

## Раздел 2. Данные и запросы

### Почему позиции встроены в заказ, а история покупателя хранится отдельными документами?

Позиции встроены в документ заказа, потому что они являются его составом. Это позволяет получать полную информацию о каждом заказе одним запросом и проводить аналитику покупок пользователя по конкретным товарам и количествам. История покупателя хранится отдельными документами, поскольку это соответствует предметной области: каждый заказ является самостоятельным событием. Кроме того, такой подход не приводит к бесконечному росту одного документа и помогает не приблизиться к ограничению MongoDB на размер документа.

### Какой факт представляет цена в позиции заказа?

`items[].price` — это цена единицы товара, зафиксированная в момент покупки. Она сохраняет фактическую стоимость продажи для последующей аналитики. Если брать цену только из текущего каталога, изменение цены в будущем могло бы исказить расчёт выручки и показать сумму, которой на самом деле не было.

## Раздел 3. Отчёт о продажах

### Пример расчёта отчёта

#### Запрос

```javascript
db.orders.aggregate(
    {$match: {
        status: "paid",
        createdAt: {
            $gte: ISODate("2026-03-01T06:00:00.000Z"),
            $lte: ISODate("2026-03-01T06:00:00.000Z")
        }
    }},
    {$unwind: {path: "$items"}},
    {$set: {revenue: {$multiply: ["$items.qty", "$items.price"]}}},
    {$group: {
        _id: "$items.sku",
        revenue: {$sum: "$revenue"},
        qty: {$sum: "$items.qty"}
    }},
    {$lookup: {
        from: "products",
        localField: "_id",
        foreignField: "_id",
        as: "product"
    }},
    {$project: {
        _id: 0,
        sku: "$_id",
        name: {$first: "$product.name"},
        qty: 1,
        revenue: 1
    }},
    {$sort: {revenue: -1, sku: 1}},
    {$limit: 5}
)
```

#### Результат

```javascript
[
    {
        revenue: Decimal128("300.00"),
        qty: 2,
        sku: "F",
        name: "Шарф"
    }
]
```

## Раздел 4. Индекс и план выполнения

Результаты запроса истории заказов (`userId: 2500`, `status: "paid"`) до и после создания составного индекса:

| Вариант | nReturned | totalKeysExamined | totalDocsExamined | Есть отдельная SORT |
|---|---:|---:|---:|---|
| До индекса | 20 | 0 | 10000 | Да |
| После индекса | 20 | 20 | 20 | Нет |

Использован индекс `{ userId: 1, status: 1, createdAt: -1, _id: 1 }`. Сначала идут поля фильтра: по `userId` и `status` выбирается нужная группа заказов. Затем указаны поля сортировки в том же направлении, что и в запросе: `createdAt` по убыванию и `_id` по возрастанию. Поэтому после фильтрации MongoDB читает записи уже в нужном порядке и отдельная стадия `SORT` не требуется. `hint` не применялся: планировщик сам выбрал созданный индекс.

До создания индекса использовался только стандартный индекс `_id`; запрос выполнял `COLLSCAN`, проверял 10 000 документов и сортировал найденные результаты. После создания индекса использовался `IXSCAN`: обследованы 20 ключей и 20 документов. Список идентификаторов и его порядок до и после индекса совпали.

Издержка индекса — дополнительное место на диске и память, а также работа при вставке, изменении или удалении заказа: индекс нужно поддерживать в актуальном состоянии.

## Раздел 6. Смена primary

Перед переключением replica set содержал три узла: один `PRIMARY` и два `SECONDARY`. Контрольный документ был записан через тот же клиент с `writeConcern: { w: "majority", j: true, wtimeout: 10000 }`. После `rs.stepDown()` клиент дождался выборов нового primary, прочитал прежний документ и записал новый документ с тем же write concern. В опыте primary изменился с `m3:27017` на `m1:27017`; оба документа присутствуют, а запись после переключения получила `acknowledged: true`.

Клиент подключён к seed list из трёх адресов с параметром `replicaSet=hw2rs`. Драйвер получает от replica set актуальную топологию, поэтому после ошибки или смены роли выбирает новый primary автоматически; адрес подключения вручную не менялся. Небольшие ошибки во время выборов обрабатываются повтором после готовности нового primary.

Подтверждение `w: "majority"` означает, что запись принята большинством узлов и переживает отказ меньшинства. Оно не означает, что чтение с произвольной secondary немедленно увидит эту запись: secondary может ещё применять oplog. Для гарантированно актуального чтения нужно читать с primary либо использовать подходящий `readConcern`/механизм causal consistency.

## Раздел 7. Шардирование

Коллекция `orders` распределена по ключу `{ userId: 1 }`.

Для истории с фильтром `{ userId: 2500, status: "paid" }` `mongos` направит запрос только на шард B: значение `2500` попадает в диапазон от `2000` включительно до `5000` исключительно. Условие по shard key позволяет выполнить точную маршрутизацию на один шард; фильтр `status` применяется уже там.

Общий отчёт с фильтром `{ status: "paid" }` не содержит условия по `userId`, поэтому `mongos` не может определить нужный диапазон shard key. Такой запрос будет scatter-gather и опросит оба шарда, A и B, после чего объединит их результаты.

Создание индекса `{ status: 1 }` внутри шардов не изменит число участников второго запроса: маршрутизация определяется shard key, а не локальными индексами. Индекс может изменить работу на каждом уже выбранном шарде — например, заменить полный просмотр локальной коллекции на индексный поиск оплаченных заказов и уменьшить число проверяемых документов.
